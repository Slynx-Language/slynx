# 3.4 Method name mangling (future/planned work)

**Status: deferred — document only, do not implement.**

This documents refactoring item 3.4 from `AcrossCodebase.md` as future work only.

## Problem

`crates/hir/src/builders/structs.rs` (`resolve_method`, ~line 109) stores method
identity by a *mangled string*: the function declaration backing a method is
registered under the symbol `"{method}_{struct}"`. That mangled symbol is the
function's `HirFunctionDeclaration.name`, and because codegen emits IR globals
from that name (`crates/codegen/src/lowerers/mod.rs` — `ir.create_function(name, …)`),
the mangling leaks into the emitted IR/output for every method call.

Mangling is a **codegen concern**: rustc only mangles at the symbol-name /
LLVM-emission stage, and keeps identity semantic inside the compiler.

Note the HIR already keys methods *semantically* in two places:

- `MethodTable::create_method(parent_type, method_name, id)` — the method lookup
  table is keyed by `(parent type, method name)`.
- Method *calls* resolve to the function's `DeclarationId` through that table and
  never rely on the mangled string to find the target.

So the only places that consume the mangled name today are:

1. The global symbol registry (`symbols_registry.get_or_insert_function`), which
   needs *some* unique key per file to avoid colliding two same-named methods on
   different structs inside one file.
2. Codegen's per-function name → `IRPointer` map and the emitted global name.

## Why the mangling in HIR is a problem

- **Identity vs. representation.** A method *is* a function whose first
  parameter is `self`. How it is lowered is an implementation detail; the HIR
  declaration should carry the semantic method name, not an encoding of its
  owner.
- **Spurious coupling.** The `{struct}` prefix is hard-coded in `resolve_method`.
  Any other future path that needs a unique *emitted* symbol (overloads,
  generics, namespaces, opt-in C ABI names) would have to side-step or reverse
  this encoding instead of producing its own symbol-name strategy.
- **Information loss.** The mangled name embeds the struct name into the
  function's identity; a rename of the struct silently changes the symbol every
  consumer sees, while the semantic `(struct, method)` pair is unchanged.

## How methods should be handled when lowering

Because a method is just a function whose first parameter is `self`, it should
be lowered exactly like any other function — the struct type is already resolved
into a typed `self` parameter during `resolve_method`:

1. **HIR stores semantic identity.** `resolve_method` registers the function
   under `method_name` (not `"{method}_{struct}"`). Uniqueness must not depend on
   mangling: either (a) keep the current **global symbol registry but key it by
   `(owner file, name)`** and rely on `MethodTable` for method resolution, or
   (b) scope the method's function declaration in a per-struct namespace inside
   the registry.
2. **Codegen produces the symbol name.** At emission time the lowerer builds the
   unique global name for a method function from its semantic name **and its
   owning struct/type** (e.g. `"{struct}_{method}"` — equivalent string, but
   produced in one place, at the boundary, instead of baked into HIR identity).
3. **Single naming function.** Add one helper, e.g. `fn global_symbol_name(hir,
   decl) -> String`, that:
   - appends nothing for free functions,
   - formats `"{struct}_{method}"` for methods (struct name from `MethodTable` or
     the `self` parameter's type),
   - and is the *only* place symbol names are produced.
4. **Method calls unchanged.** Call lowering already resolves the target through
   `MethodTable` to a `DeclarationId`; the mapper in
   `crates/codegen/src/lowerers/expressions.rs` (`self.functions[&name]`) would
   key by the codegen-side symbol instead of the HIR name pointer.

## Why this is deferred

Implementing it changes function-identity keying across three crates at once:
the HIR symbol registry (uniqueness without mangling), the monomorphizer (which
looks functions up by name), and codegen's name→pointer maps + emitted globals.
That is a cross-cutting redesign, not a small mechanically-verifiable fix, and
so is intentionally left out of the current maintenance pass — particularly
since methods are already resolved semantically via `MethodTable`, so no current
behavior depends on the mangled string except the emitted symbol name.
